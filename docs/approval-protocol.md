# Interactive approval protocol (in progress)

The default runner adapters do **not** provide interactive approvals. Claude runs with permission prompts disabled, and Codex normally uses its non-interactive CLI. An experimental Codex app-server transport can be selected in the desktop worker settings or for a CLI worker with `XENIA_CODEX_APP_SERVER=1`; it is not yet a supported release path. Use disposable repositories only while testing it.

The controller stores each request with a generated UUID, job ID, node ID, worker instance ID, kind, and JSON details. Workers may create or poll requests only for their own node and its current instance. Replaying a request UUID with identical contents returns the existing decision; changing any of its contents is rejected. Only a running job may create requests, and a job is limited to 32 pending requests. Request details are limited to 64 KB and stored in the controller database, so they require the same protection and backup treatment as prompts and output.

Only the operator credential may list or decide requests. Decisions are `accept` or `decline`, apply to one request, and are persisted before acknowledgement. Repeating the same decision is idempotent; attempting to change a decision is rejected. The controller accepts approval for a Codex command with a nonempty command and working directory, a Claude Bash tool request with a nonempty command, or a file change with a nonempty diff; network and non-command variants are deny-only until their semantics are supported. Lists retain a recorded decision until the worker acknowledges delivery; that acknowledgement means it was written to the runner's input, not that an action executed. The worker persists acknowledgements in its outbox; a late acknowledgement for its original instance is accepted after takeover because it cannot grant permission. Lists and new decisions exclude canceled, completed, unknown, or fenced jobs. Poll responses include an `active` flag: a worker must not apply a returned decision unless it is true. A decision already delivered to a runner can race with cancellation; cancellation is not a retroactive revocation.

Before enabling this for real work, the adapter must bind each runner callback to a fresh request UUID, supply complete and accurate details for the action, reject unsupported or incomplete requests, honor cancellation and lost connections, and report outcomes without automatically approving broader session or policy changes. Restart, fencing, concurrent requests, oversized details, real-runner compatibility, and native Windows behavior require end-to-end tests.

The experimental Codex app-server transport checks the returned thread, working directory, workspace-write sandbox, and on-request approval policy, maps streamed message deltas, and rejects unknown server requests. It keeps the worker credential in Xenia, uses the worker instance to fence approval callbacks, and acknowledges a decision after writing it to the runner. File-change requests are deliberately deny-only until Xenia can correlate and present the complete patch without a race. A synthetic app-server test covers approvals, cancellation, controller restart, and follow-up; the installed Codex CLI has completed disposable edits and follow-ups through this transport. A disposable real Codex run also presented and accepted a narrowly scoped harmless shell command, and a separate run declined it. Broader real-provider approval scenarios and native Windows execution still need verification. To exercise the installed Codex CLI's initialization without an authenticated profile, run `cargo test codex_protocol::tests::installed_app_server_initializes_with_expected_policy -- --ignored`.

The Claude worker limits outstanding callbacks to 32, including canceled callbacks still awaiting withdrawal; if that limit is reached it fails the run rather than allowing the queue to grow without bound. A current worker instance may withdraw a registered request after the runner cancels its callback. Withdrawal is idempotent, hides the request, rejects later operator decisions, and makes polling report it inactive even if a decision was already stored. A worker must discard any locally queued response when the runner cancels it; withdrawal cannot retract bytes already delivered. The Claude transport serializes registration and withdrawal: if a registration may have succeeded despite a lost response, it retries it before withdrawing. The endpoint intentionally does not create tombstones for unknown IDs.

## Claude Code integration work remaining

Claude's [Agent SDK approval interface](https://code.claude.com/docs/en/agent-sdk/user-input) delivers both tool permissions and `AskUserQuestion` through `canUseTool`. The callback is not invoked for actions already allowed by the active permission rules or mode. Xenia must preserve the whole tool name and input for an individual decision, handle questions as questions rather than treating them as commands, and never turn a single approval into a persistent permission rule. The controller can store and replay structured question answers with the same worker-instance fencing as approvals, the PWA can submit them, and the experimental worker can deliver them to Claude; Claude Bash requests can be approved individually after review; other Claude tool requests remain deny-only.

The [SDK's control transport](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/query.py) uses a bidirectional stream, correlates control requests by ID, and keeps stdin open while callbacks are pending. This is an implementation detail rather than a published Rust SDK contract; a direct Rust implementation would need version checks and real CLI contract tests, including canceled callbacks and background tasks that continue after a result frame. An alternative SDK-based bridge would add a runtime dependency to native worker packages. The direct transport is available through an experimental desktop worker setting or to CLI workers with `XENIA_CLAUDE_CONTROL=1`. It uses `acceptEdits`, presents questions and individual Bash requests, and makes other permission requests deny-only. The Bash callback does not report the shell’s current working directory, which may have changed; the UI states this limitation and displays the full callback. Synthetic integration tests cover a controller restart during a question, deny-only tool requests, runner withdrawal, and cancellation while waiting. It has not been validated for all request types, cancellation races, or native Windows and is not a release path. The installed CLI completed an initial conversation, follow-up, and a question answered through Xenia in disposable repositories; another real run was canceled while waiting for a question response. A separate disposable run accepted a single exact Bash request and verified its harmless marker output. `python3 tests/claude_control_contract.py` is an opt-in real-provider contract check: it uses an authenticated Claude CLI, submits a model request in a disposable checkout, denies every callback, and verifies that the requested file was not created. It can be inconclusive if Claude chooses a different action and consumes model usage. The installed CLI passed initialization and a denied Bash callback with `--permission-prompt-tool stdio`; the separate real question run verified a narrow Xenia integration.
